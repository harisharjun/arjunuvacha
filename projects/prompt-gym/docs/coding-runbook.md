# PromptGym — coding runbook

Ten sessions, roughly 13 hours total, which is two weekends at your pace. Each session is self-contained: setup commands, a prompt to paste into Claude Code, what to review before accepting, and a done-when test you can run. Stop at the done-when and commit. Do not carry a session over — an unfinished milestone is easier to restart than to resume.

The design doc is the spec. The build guide explains the hard parts. This file is just the order of operations.

---

## Before session 1 — the repo's house rules

Create `CLAUDE.md` at the repo root before writing any code. Every Claude Code session reads it automatically, which means you stop re-explaining the same constraints and it stops making the same class of mistake.

```markdown
# PromptGym — working rules

## Runtime
This project targets the **Cloudflare Workers edge runtime**, NOT Node.js.
There is no `fs`, no `child_process`, no `node:crypto`, no `Buffer`, no `eval`
or `new Function`. Use WebCrypto (`crypto.subtle`), `fetch`, `TextEncoder`.

Before proposing ANY npm dependency, state whether it runs on the Workers
runtime without the `nodejs_compat` flag. If it does not, propose the
hand-rolled WebCrypto equivalent instead. This Worker should ship with
essentially zero runtime dependencies.

## Source of truth
- `design-doc.md` is the spec. Read it before proposing architecture.
- Challenges are authored as `challenges/*.promptfoo.yaml`. These are CONTENT.
  Never edit a challenge file to make an implementation pass — if a test case
  seems wrong, stop and ask.
- Runtime JSON is generated by `build/convert.mjs`. Never hand-edit generated
  JSON.

## Grading engine
`worker/src/grading/` must stay pure: no network, no I/O, no global state.
Every function takes inputs and returns outputs. This is what makes it
testable for free, and scores depend on it being right.

## Security boundaries — do not weaken these without asking
- Hidden test inputs and expected values are filtered server-side by each test
  case's `reveal` level, BEFORE serialising the response. Never send hidden
  data to the browser to be hidden in the UI.
- Validator functions are looked up by name from a compiled registry. Never
  execute a function body that came from data.
- A user's own Groq API key is request-scoped: never written to the database,
  never logged, never included in an error message or response body.

## Failure semantics
An upstream failure (Groq 5xx, timeout, unparseable judge output) is
`errored`, NOT `failed`. A user's prompt must never be scored down because our
infrastructure had a bad moment. A run containing any `errored` grader is not
eligible for the leaderboard.

## Testing
Unit tests must not call the Groq API. Stub the provider and replay recorded
fixtures. The live API budget is small and the deployed site needs it.

## Style
TypeScript, ES modules. Small files. Prefer explicit over clever.
```

## Session 2 · The grading engine
**~2.5 hrs · Milestone M1 · The session that matters most**

Have `pg-a1-address-extractor.json` open — you will hand it over as the format reference.

**Paste into Claude Code:**

> Milestone M1: the grading engine. Read `challenge-format.md` first, and use `challenges/pg-a1-address-extractor.json` as the authoritative example of the runtime format.
>
> Build `worker/src/grading/` as pure TypeScript functions — no network, no I/O. Write the tests FIRST, then the implementation.
>
> Assertion types to support: `equals`, `contains`, `icontains`, `contains-all`, `contains-any`, `starts-with`, `regex`, `word-count` (accepts a number or `{min,max}`), `is-json` (with a minimal JSON-schema subset: `type`, `required`, `properties`, `enum`, `pattern`, `additionalProperties`), and `javascript` (resolved by name from a registry — never from a string body). Support a `not-` prefix on every applicable type. Also implement `levenshtein` and `rouge-n` in pure JS.
>
> Scoring: each assertion yields 0–1. Per test case, `score = sum(assertionScore × weight) / sum(weight)`. Challenge score is `round(100 × mean(caseScores))`. A case where every assertion fails scores 0, never NaN.
>
> Tests must cover: every assertion type, the `not-` variants, weights actually affecting the result, `additionalProperties: false` rejecting extra keys, `pattern` being enforced, and malformed model output (not JSON at all) failing cleanly rather than throwing.
>
> Do not add dependencies — no ajv, no lodash.

**Review this yourself, properly.** Three specific things, because a bug here silently corrupts every score on the leaderboard:

1. **Weights are applied.** Change a weight from 3 to 6 in a fixture and confirm the score moves. Generated code often accepts `weight` and then ignores it.
2. **Division by zero.** A test case with no assertions, or all zero weights, must not produce `NaN` — trace that path by hand.
3. **`additionalProperties: false` actually rejects.** This is the most commonly stubbed-out schema keyword. Write the failing case yourself if the tests do not have one.

**Done when:** `npm test` is green and you have personally read `grading/score.ts` and the schema validator end to end.

```bash
git commit -m "M1: grading engine, pure functions, full assertion coverage"
```

## Session 3 · The converter, and all 12 challenges converted
**~1 hr · Milestone M1 part two**

**Paste into Claude Code:**

> Write `build/convert.mjs` — a Node script (this one runs on your laptop, not on Workers, so Node APIs are fine here).
>
> It reads a `challenges/*.promptfoo.yaml` file and emits the runtime JSON described in `challenge-format.md`. Transformations: lift `defaultTest.assert` to a top-level `defaultAssert`; move each `tests[].metadata.reveal` to `tests[].reveal`; and replace every inline `javascript` assertion `value` with `{"ref": "<name>"}` where the name comes from the `# ref:` comment directly above that assertion in the YAML.
>
> It must import the validator registry from `worker/src/grading/validators.ts` and verify that every `ref` it emits exists there. If any does not, print which challenge and which ref, and exit non-zero.
>
> Verify it against the hand-written `challenges/pg-a1-address-extractor.json`: parsed output must deep-equal the committed file after stripping all keys beginning with `$` from both. Do not try to match byte-for-byte — the `$comment` and `$validators` blocks are human documentation and the converter is not expected to reproduce them.
>
> Then extract every inline validator body from all 12 challenge YAMLs into the registry under its `# ref:` name, run the converter over all of them, and report any refs that are missing.

**Done when:** all 12 challenges convert cleanly and the A1 deep-equal check passes.

## Session 4 · Groq client
**~1 hr · Milestone M2**

```bash
npx wrangler secret put GROQ_API_KEY   # paste your key when prompted
```

**Paste into Claude Code:**

> Milestone M2. Build `worker/src/providers/groq.ts` with two functions: `execute({prompt, input, model, apiKey, maxOutputTokens})` and `judge({output, rubric, model, apiKey})`. Both call Groq's OpenAI-compatible chat completions endpoint at temperature 0, using `fetch`.
>
> Rules: reject prompts over 2000 characters before making any call; apply `maxOutputTokens` from the challenge; 20-second timeout via `AbortController`.
>
> Error handling, using typed error classes: on HTTP 429, read the `retry-after` header, retry exactly once after that delay, and throw `RateLimitedError` if it fails again. On 5xx or timeout, throw `UpstreamError`. Never include the raw upstream response body in a thrown error — it can echo the API key.
>
> `judge` must return strict JSON — `{pass: boolean, reason: string}` or `{score: number, reason: string}`. On unparseable output, retry once with a stricter format instruction, then throw `JudgeError`.
>
> Model these so an `errored` result is structurally distinct from a `failed` one — it must be impossible to aggregate an errored case into a numeric score. Then write `scripts/try-challenge.mjs` that grades one challenge end to end against real Groq and prints the scorecard.

**Done when:**

```bash
node scripts/try-challenge.mjs pg-a2 --prompt-file reference.txt   # scores high
node scripts/try-challenge.mjs pg-a2 --prompt "Please categorise this ticket."  # scores low
```

That gap is your first real evidence the whole idea works.

```bash
git commit -m "M2: groq client, typed errors, errored vs failed"
```

**Paste into Claude Code:**

> Milestone M3. Add `POST /api/run` accepting `{challengeId, prompt, model}` and an optional `X-Groq-Key` header. No auth, no database yet.

## Session 7 · Auth
**~1.5 hrs · Milestone M5 · Read every line of this one**

In the Firebase console, enable the Google and Anonymous sign-in providers first.

**Paste into Claude Code:**

> Milestone M5. In `web/`, sign in anonymously via Firebase Auth on first load, and add a sign-in-with-Google button that **links** the anonymous account rather than replacing it, so scores survive. Send the ID token as `Authorization: Bearer`.
>
> In `worker/src/auth/`, verify the token using WebCrypto only — `firebase-admin` does not run on the Workers runtime. Fetch the JWKS from `https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com`, import keys with `crypto.subtle.importKey('jwk', ...)`, verify RS256 with `crypto.subtle.verify`, and cache the JWKS in the Cache API honouring its `max-age`.
>
> Validate every claim: `alg` is RS256; `kid` from the token header **selects** the key (do not try all keys); `iss` equals `https://securetoken.google.com/<projectId>`; `aud` equals `<projectId>`; `exp` is in the future; `iat` is in the past; `sub` is non-empty. Reject on any failure. A missing or malformed Authorization header means an anonymous request, not an error — anonymous play must keep working.
>
> Write a test using a token with a valid signature but the wrong `aud`, and assert it is rejected.
>
> On success, upsert the user and write `best_scores` — but only for runs with no `errored` graders.

**Review by hand, all four:**

- `kid` selects the key. Code that loops over all keys accepts tokens signed by the wrong one.
- `aud` and `iss` are compared against your project ID, not merely parsed.
- Expiry is checked. This gets skipped surprisingly often.
- No Authorization header degrades to anonymous rather than throwing.

**Done when:** signing in with Google preserves anonymous scores, and the wrong-`aud` test fails closed.

```bash
git commit -m "M5: firebase id token verification via webcrypto, account linking"
```

## Rules that keep this on track

**Commit at every done-when.** These are your rollback points, and with generated code you will want them.

**One session, one milestone.** If a session starts drifting into the next milestone, stop it. The review step is where you actually learn the architecture, and review stops happening once the diff passes a few hundred lines.

**Never let it edit a challenge YAML.** If an implementation cannot pass a test case, the implementation is wrong — or the challenge is genuinely flawed and you should decide that deliberately, not let it get quietly softened to make a build green.

**Run the tests yourself before accepting.** Not "it says tests pass" — run them.

**If you only get two hours one weekend**, do session 2. The grading engine is the project. Everything else is plumbing around it, and plumbing is much easier to generate.
