# PromptGym — working rules

## Runtime
This project targets the **Cloudflare Workers edge runtime**, NOT Node.js.
There is no `fs`, no `child_process`, no `node:crypto`, no `Buffer`, no `eval`
or `new Function`. Use WebCrypto (`crypto.subtle`), `fetch`, `TextEncoder`.

Before proposing ANY npm dependency, state whether it runs on the Workers
runtime without the `nodejs_compat` flag. If it does not, propose the
hand-rolled WebCrypto equivalent instead. This Worker should ship with
essentially zero runtime dependencies.

Exception: `build/` and `scripts/` run on the laptop under real Node, so Node
APIs are fine there and only there.

## Source of truth
- `docs/design-doc.md` is the spec. Read it before proposing architecture.
- Challenges are authored as `challenges/*.promptfoo.yaml`. These are CONTENT.
  Never edit a challenge file to make an implementation pass — if a test case
  seems wrong, stop and ask.
- Runtime JSON is generated by `build/convert.mjs` into `challenges/generated/`.
  Never hand-edit generated JSON.

## Locked decisions that contradict what the files say
- **Reveal levels: v1 ships `partial` for EVERY test case**, uniformly. The
  `metadata.reveal` values in the challenge YAMLs (`full`, `verdict-only`) are
  a deferred target policy, deliberately left in place. Implement uniform
  `partial`; do not honour the per-case values, and do not edit the YAMLs to
  match. See `docs/challenge-format.md` §5.
- **Passing a challenge unlocks the reference prompt only.** Hidden inputs and
  expected values stay hidden even after a pass.
- **Leaderboard decay: model column + asterisk.** Never re-grade historical
  submissions, no seasons. Show which execution model earned each score.

## Grading engine
`worker/prompt-gym/src/grading/` must stay pure: no network, no I/O, no global
state. Every function takes inputs and returns outputs. This is what makes it
testable for free, and scores depend on it being right.

## Security boundaries — do not weaken these without asking
- Hidden test inputs and expected values are filtered server-side by each test
  case's `reveal` level, BEFORE serialising the response. Never send hidden
  data to the browser to be hidden in the UI.
- Validator functions are looked up by name from a compiled registry. Never
  execute a function body that came from data.
- A user's own Groq API key is request-scoped: never written to the database,
  never logged, never included in an error message or response body.

## Failure semantics
An upstream failure (Groq 5xx, timeout, unparseable judge output) is
`errored`, NOT `failed`. A user's prompt must never be scored down because our
infrastructure had a bad moment. A run containing any `errored` grader is not
eligible for the leaderboard.

## Testing
Unit tests must not call the Groq API. Stub the provider and replay recorded
fixtures. The live API budget is small and the deployed site needs it.

## Style
TypeScript, ES modules. Small files. Prefer explicit over clever.
